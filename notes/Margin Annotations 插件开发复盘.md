# Margin Annotations 插件开发复盘

这篇笔记记录一次完整的 Obsidian 插件开发过程：从“我想在笔记两侧留白处写批注”这个需求开始，一步步变成一个可用的本地插件 `Margin Annotations`。

这个插件的核心目标不是复刻 Cornell Marginalia，而是走一条更符合直觉的路：

- 选中文字
- 右键添加旁注
- 旁注出现在左右留白
- 旁注可以编辑、删除、移动
- 正文尽量保持干净
- 不强迫用户记快捷键或手写语法

## 最初需求

读论文时，Obsidian 页面左右两边有留白。我希望像读纸质书一样，对某个词、某句话、某个概念直接做旁注。

一开始的真实需求不是“我要做插件”，而是：

> 我选中一个词或句子，希望能在旁边写一点自己的理解、疑问、反驳、例子。

这个需求包含几个隐含要求：

- 旁注必须跟原文位置绑定。
- 原文必须被高亮，否则不知道旁注对应哪里。
- 注释最好显示在留白，而不是挤在正文下面。
- 添加操作要自然，最好右键就能完成。
- 后续必须能编辑、删除。
- 编辑模式不能太难看。

## 为什么参考 Cornell Marginalia

Cornell Marginalia 是一个已经成熟的 Obsidian 旁注插件。它提供了 Cornell 风格的边注能力，但它的核心交互偏向语法和快捷键。

它的典型方式类似：

```markdown
%%> 这里是旁注 %%
```

它的优势：

- 成熟度高。
- 功能很多。
- 有阅读模式、编辑模式、导出、复习、Doodle、Dashboard 等扩展能力。
- 已经处理了很多 Obsidian 场景。

它的问题：

- 对普通用户来说，快捷键和语法门槛偏高。
- 添加旁注不够“顺手”。
- 它更像一个大而全的学习系统，而不是轻量、直接的研读批注工具。

所以我这里的定位不是照抄它，而是：

> Cornell Marginalia 是参照物，不是终点。我的路线是右键交互、直觉操作、正文干净。

## 产品方向的差异

这次插件的方向可以总结为：

| 维度 | Cornell Marginalia | Margin Annotations |
|---|---|---|
| 添加方式 | 快捷键、命令、语法 | 选中文字后右键 |
| 用户门槛 | 偏高 | 偏低 |
| 主要场景 | Cornell 学习系统 | 论文研读、词句批注 |
| 存储方式 | Markdown 内嵌语法 | 插件数据外置 |
| 操作方式 | 命令较多 | 鼠标右键为主 |
| 目标体验 | 功能丰富 | 顺手、干净、可视化 |

这就是“原创性”的基础：不是功能点完全没人做过，而是用自己的用户体验路径重做这个问题。

## 第一阶段：最小可用原型

第一版的目标很简单：先让右键添加旁注跑通。

实现点：

1. 监听 Obsidian 的 `editor-menu`。
2. 判断当前是否选中文字。
3. 如果有选区，就在右键菜单里插入：
   - 添加右侧旁注
   - 添加左侧旁注
4. 用户点击后弹出输入框。
5. 保存后把选中的文字替换成高亮和旁注标记。

早期 Markdown 结构大概是：

```markdown
==选中文字==<span class="ma-anchor" data-ma-id="ma-xxx"></span> %%ma:right:ma-xxx: 旁注内容 %%
```

这里有三个部分：

- `==选中文字==`：Obsidian 原生高亮。
- `<span class="ma-anchor"...>`：定位锚点。
- `%%ma:...%%`：插件自己的旁注数据。

这个版本的优点是简单直接，能很快看到效果。

但问题也明显：

- 正文被插件语法污染。
- 编辑模式里会看到奇怪的 `%%ma...%%`。
- 用户体验像“能用的技术原型”，不是一个真正舒服的产品。

## 第二阶段：输入框重做

最开始尝试过 Obsidian 原生 Modal 或简单 prompt，但实际体验很差：

- 点击菜单后弹窗不稳定。
- 有时输入框无法输入。
- 焦点被 Obsidian 编辑器抢走。
- 视觉上不自然。
- 弹窗里只有一个细细的输入条，体验很糟。

于是改成自定义浮层 composer。

它的核心设计：

- 使用 `position: fixed` 覆盖在 Obsidian 上方。
- 自己创建 `textarea`。
- 阻止键盘事件继续冒泡到 Obsidian。
- 支持 `Ctrl + Enter` 保存。
- 点击外部关闭。
- 保留选中文本预览。

这一步的意义是：

> 插件的基础交互不能依赖一个不稳定的输入弹窗，必须先把“写旁注”这件事做顺。

后来媒体、颜色都是在这个 composer 上继续扩展的。

## 第三阶段：阅读模式旁注渲染

接下来要把旁注真正显示到留白处。

基本思路：

1. 在阅读模式的 Markdown 渲染完成后，插件拿到 HTML。
2. 找到正文里的 `.ma-anchor`。
3. 根据 anchor 的位置找到它所在段落、标题或列表项。
4. 在这个元素旁边插入一个旁注容器。
5. 右侧旁注用 CSS 放到正文右边。
6. 左侧旁注用 CSS 放到正文左边。

核心 CSS 思路：

```css
.ma-reading-container {
  position: relative;
}

.ma-col-right {
  position: absolute;
  left: calc(100% + var(--ma-margin-gap));
}

.ma-col-left {
  position: absolute;
  right: calc(100% + var(--ma-margin-gap));
}
```

这一步让旁注第一次真正“长在留白里”。

## 第四阶段：编辑模式隐藏丑语法

早期最难看的地方是编辑模式。

用户会看到类似：

```markdown
%%ma:right:ma-xxx: 你好 %%
```

这会严重破坏写作和阅读体验。

为了解决这个问题，引入了 CodeMirror extension。

思路：

- 扫描编辑器可见区域。
- 找到插件生成的 anchor 和旧版注释标记。
- 用 `Decoration.replace({})` 把这些原始语法隐藏掉。

这一步让 Live Preview 里不再直接暴露插件内部标记。

但它只是“隐藏”，不是根本解决。因为旁注内容仍然写在 Markdown 里。

## 第五阶段：编辑和删除交互

一开始旁注卡片上出现过可见的“编辑”和“删除”按钮。

问题：

- 旁注卡片变得像工具栏。
- 按钮占据视觉空间。
- 读文章时干扰很强。
- 留白批注应该轻，而不是每条批注都显得很重。

后来改成：

- 旁注卡片上不显示按钮。
- 右键旁注才出现菜单。
- 菜单里提供：
  - 编辑旁注
  - 移到左侧 / 右侧
  - 删除旁注

这个改变很关键，因为它确立了插件的交互原则：

> 添加时右键正文，管理时右键旁注。

这比把按钮堆在界面上更干净。

## 第六阶段：0.7 架构升级，旁注外置存储

这是整个插件最重要的一次架构升级。

早期旁注内容保存在 Markdown 里：

```markdown
==选中文字==<span class="ma-anchor" data-ma-id="ma-xxx"></span> %%ma:right:ma-xxx: 你好 %%
```

后来改成：

```markdown
==选中文字==<span class="ma-anchor" data-ma-id="ma-xxx"></span>
```

旁注正文、方向、颜色等数据保存在插件自己的 `data.json` 里。

数据大概长这样：

```json
{
  "files": {
    "论文积累/两种不同的攻击评判标准.md": {
      "ma-xxx": {
        "id": "ma-xxx",
        "side": "right",
        "note": "你好",
        "quote": "公平的评估环境",
        "color": "#ffe066",
        "createdAt": "2026-05-25T...",
        "updatedAt": "2026-05-25T..."
      }
    }
  }
}
```

这样做的好处：

- Markdown 正文更干净。
- 旁注内容不会挤在原文下面。
- 编辑模式体验明显提升。
- 后续扩展颜色、媒体、标签、管理面板更容易。

这样做的代价：

- 旁注变得依赖插件数据。
- 必须考虑导出和备份。
- 如果原文被大改，anchor 可能需要修复机制。

这一步让插件从“Markdown 小技巧”变成了“真正的插件系统”。

## 第七阶段：旧数据迁移

因为前面已经产生过旧格式：

```markdown
%%ma:right:ma-xxx: 你好 %%
```

所以必须支持迁移。

迁移逻辑：

1. 扫描 Markdown 文件。
2. 查找旧版 `%%ma:...%%` 标记。
3. 读取其中的 side、id、note。
4. 把 note 写入插件数据。
5. 删除正文里的旧旁注内容。
6. 保留 anchor。

这一步的意义是：

> 原型阶段留下的数据不能被抛弃，插件升级要尽量向前兼容。

## 第八阶段：0.8 设置系统

后来补了设置页。

设置页包含：

- 阅读模式是否显示旁注
- 编辑模式是否显示旁注
- 默认旁注方向
- 旁注宽度
- 正文与旁注间距
- 旁注字号
- 媒体最大高度
- 媒体附件目录
- 是否自动迁移旧版行内旁注

为什么设置系统重要：

- 不同用户屏幕宽度不同。
- 不同主题字体大小不同。
- 有人希望编辑模式显示旁注，有人不希望。
- 媒体附件目录必须可配置。

这一步让插件从“作者自己能用”变成“别人也可能能用”。

## 第九阶段：0.8 媒体能力

接着加了媒体旁注。

目标：

> 旁注不只写文字，也能放截图、图片、音频、视频、PDF。

实现方式：

1. 在旁注输入框中加入 `添加媒体` 按钮。
2. 支持选择文件：
   - 图片
   - 音频
   - 视频
   - PDF
3. 支持直接粘贴截图。
4. 插件把文件保存到附件目录。
5. 在旁注内容中插入 Obsidian embed 语法。

例如：

```markdown
![[Margin Annotations Attachments/example.png]]
```

旁注内容通过 Obsidian 的 `MarkdownRenderer.render` 渲染，所以图片和媒体可以正常显示。

这一步让旁注从“文字批注”扩展成“多媒体证据卡片”。

## 第十阶段：0.9 颜色系统

后来加了颜色功能。

这里没有做成全局颜色，而是每一条旁注都可以有自己的颜色。

原因：

- 同一篇文章里，不同批注可能有不同含义。
- 黄色可以表示重点。
- 蓝色可以表示疑问。
- 绿色可以表示已理解。
- 粉色可以表示待查。
- 紫色可以表示概念关联。

实现点：

- 数据里新增 `color` 字段。
- 新建旁注时可以选颜色。
- 右键旁注可以改颜色。
- 设置页可以设置默认颜色。
- 阅读模式高亮跟随颜色。
- 编辑模式高亮跟随颜色。
- 旁注边线跟随颜色。

颜色数据示例：

```json
{
  "id": "ma-xxx",
  "side": "right",
  "note": "这里是一个关键概念",
  "quote": "公平的评估环境",
  "color": "#74c0fc"
}
```

## 第十一步：颜色按钮样式修复

颜色功能加完后，出现了一个实际问题：

> 颜色按钮存在，但看起来全是白圈。

原因是 Obsidian 默认按钮样式覆盖了色块的背景。

修复方式：

- CSS 里对色块背景使用 `!important`。
- JS 里也给每个按钮写入内联背景色。
- 给边框也加上颜色。

这一步说明一个很现实的问题：

> 在 Obsidian 插件里，很多 bug 不是逻辑错，而是被主题或默认样式覆盖。

## 第十二阶段：缩放和响应式问题

后来发现全屏正常，但窗口缩放后，旁注跑到正文下面。

原因是早期 CSS 有一个响应式规则：

```css
@media (max-width: 1180px)
```

窗口缩放后，CSS 视口宽度变小，插件误以为当前是窄屏，于是把旁注折叠到正文下面。

这本来是为了保护小屏幕体验，但阈值太高。

后来改成：

```css
@media (max-width: 760px)
```

这样：

- 桌面缩放时，旁注仍然留在左右留白。
- 真正很窄的窗口才会折叠进正文。

这一步说明：

> 响应式不是越早折叠越好，要符合用户的真实使用场景。

## 开发中踩过的坑

### 1. 输入框看得见但不能输入

原因通常是 Obsidian 编辑器抢焦点，或者事件冒泡被父级处理。

解决方式：

- 自己写 composer。
- textarea 阻止键盘事件冒泡。
- 显式 focus。

### 2. 编辑模式出现丑陋语法

原因是插件把数据写进 Markdown。

解决方式：

- 先用 CodeMirror decoration 隐藏。
- 后来改为外置数据存储。

### 3. 编辑/删除按钮破坏旁注美感

原因是操作按钮直接显示在卡片上，视觉负担太重。

解决方式：

- 改成右键菜单。

### 4. 色块全部显示成白色

原因是 Obsidian 默认按钮背景覆盖自定义颜色。

解决方式：

- CSS 加强优先级。
- JS 写入内联背景色。

### 5. 缩放窗口后旁注跑到正文下面

原因是响应式阈值太高。

解决方式：

- 折叠阈值从 `1180px` 降到 `760px`。

## 和 Cornell Marginalia 的当前差距

目前还不如 Cornell 的地方：

- 没有全库旁注管理面板。
- 没有复杂筛选和搜索。
- 没有复习系统。
- 没有 Anki 同步。
- 没有成熟的导出系统。
- 没有 PDF 专门批注系统。
- 没有长时间、多主题、多设备兼容性测试。

但当前插件已经比 Cornell 更适合一个核心场景：

> 读文章时，直接选中文字，右键写旁注。

这就是它的独特方向。

## 下一步路线

### 1. 旁注管理面板

目标：

- 显示当前笔记所有旁注。
- 显示全库所有旁注。
- 支持搜索。
- 支持按颜色筛选。
- 点击旁注跳转原文位置。

这是从“批注工具”升级到“知识管理工具”的关键一步。

### 2. 颜色语义系统

现在颜色只是颜色，以后可以给颜色命名：

| 颜色 | 含义 |
|---|---|
| 黄色 | 重点 |
| 蓝色 | 疑问 |
| 绿色 | 已理解 |
| 粉色 | 待查 |
| 紫色 | 概念关联 |
| 橙色 | 反驳或风险 |

这样颜色就不只是视觉效果，而是学习流程的一部分。

### 3. 导出系统

因为旁注内容保存在插件数据里，所以以后必须能导出。

可能的导出形式：

- 导出为普通 Markdown。
- 导出为带脚注的 Markdown。
- 导出为左右分栏 HTML。
- 导出为适合 PDF 打印的格式。

### 4. 锚点修复

现在旁注靠 anchor 绑定。

如果用户大幅修改原文，anchor 可能丢失。

未来可以根据 `quote` 字段尝试重新定位：

- 精确匹配原文。
- 模糊匹配相似文本。
- 提示用户手动重新绑定。

### 5. 批注工作流

可以进一步把旁注分成状态：

- 未处理
- 已理解
- 待复习
- 待查资料
- 可转为永久笔记

这样就不只是“写旁注”，而是变成完整的阅读处理流程。

## 最重要的经验

这次开发最重要的经验不是某个 API，而是产品路线：

> 先让核心交互顺手，再补架构；先解决真实痛点，再追求功能完整。

一开始的版本确实粗糙，甚至有很多难看的地方。但每一次不舒服的反馈，都变成了下一版的产品判断：

- 不能输入，说明输入框必须重做。
- 语法难看，说明数据不能塞正文。
- 按钮碍眼，说明操作应该放右键菜单。
- 颜色不可见，说明插件必须考虑 Obsidian 样式覆盖。
- 缩放错位，说明响应式阈值要基于真实使用场景。

所以前面的版本不是白做，而是在快速验证：

- 用户到底想怎么用。
- 哪些体验不能接受。
- 哪些功能才是核心。
- 插件架构应该往哪里走。

## 一句话总结

Margin Annotations 的路线不是做 Cornell Marginalia 的替代品，而是做一个更适合普通研读场景的旁注工具：

> 选中文字，右键添加，留白显示，干净编辑，后续可管理。

这条路还没走完，但核心方向已经成立。
